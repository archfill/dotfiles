すべての変更を分析し、論理的に関連するグループに分割して、複数のコミットを作成してください。

## 言語設定

- **デフォルト: 日本語**
- 引数 `$ARGUMENTS` を確認:
  - `--en` が含まれる場合 → 英語でメッセージ作成
  - `--ja` または指定なし → 日本語でメッセージ作成

## 手順

1. **変更の全体把握**
   - `git status` で全変更を確認
   - `git diff` で未ステージの差分を確認
   - `git diff --cached` で既にステージ済みの差分も確認

2. **変更の分析とグルーピング**
   各変更を以下の観点で分類:
   - 機能/モジュール単位（同じ機能に関する変更）
   - 変更の種類（新機能、バグ修正、リファクタリング等）
   - 依存関係（一緒にコミットすべき関連変更）

3. **コミット計画の提示**
   分析結果をユーザーに提示:
   ```
   ## 提案するコミット分割

   ### コミット 1: feat(auth): ログイン機能を追加
   - src/auth/login.ts
   - src/auth/types.ts

   ### コミット 2: fix(api): エラーハンドリングを修正
   - src/api/client.ts

   ### コミット 3: chore(config): 設定ファイルを更新
   - config/settings.json
   ```

4. **ユーザー確認**
   - 提案した分割でよいか確認
   - 必要に応じて調整

5. **順次コミット実行**
   承認後、各グループを順番にコミット:
   - `git add <files>` で対象ファイルをステージング
   - `git commit -m "..."` でコミット
   - 次のグループへ

## グルーピングの指針

### 同じコミットに含めるべき
- 同一機能の実装ファイルとテスト
- 型定義とその実装
- 設定変更とそれに依存するコード
- リネーム/移動とインポートパスの更新

### 分割すべき
- 異なる機能の変更
- 独立したバグ修正
- フォーマット/リント修正と機能変更
- ドキュメント更新と実装変更

## Conventional Commits形式

```
<type>(<scope>): <subject>

<body>
```

### Type
- `feat`: 新機能
- `fix`: バグ修正
- `docs`: ドキュメントのみの変更
- `style`: コードの意味に影響しない変更
- `refactor`: バグ修正でも機能追加でもないコード変更
- `perf`: パフォーマンス改善
- `test`: テストの追加・修正
- `chore`: ビルドプロセスやツールの変更
- `ci`: CI設定の変更

### 言語別の書き方

**日本語の場合:**
```
feat(nvim): プラグインの遅延読み込みを追加
```
- subjectは体言止め（「〜を追加」「〜を修正」）

**英語の場合:**
```
feat(nvim): add lazy loading for plugins
```
- subjectは命令形・小文字開始（add, fix, update）

### 注意事項

- 各コミットは独立して意味を持つようにする
- 依存関係のあるコミットは正しい順序で実行
- **機密情報を含むファイルがないか各コミット前に確認**
- コミット間でビルドが壊れないよう配慮
- Co-Authored-ByとGenerated with行は**絶対に追加しない**
